# Migration Guides

This directory holds operational migration scripts. Each is one-shot —
run when the trigger condition is met, then keep the file in source for
reference.

## When to migrate to Postgres + TimescaleDB

You don't need this for development or small production deployments.
Triggers that mean it's time:

1. **Users > 500** — SQLite's single-writer lock starts causing visible
   latency under concurrent traffic.
2. **`ohlcv_bars` > 5 GB** — query latency on date-range scans becomes
   noticeable.
3. **Multi-worker scaling needed** — running 2+ uvicorn workers against
   SQLite is unsafe (file locking can corrupt the DB under high
   concurrency). Postgres has no such limit.
4. **Frontend showing "DB busy" errors** — usually first sign you're
   hitting the write-lock ceiling.

If none of these apply, **stay on SQLite**. It's faster than Postgres
for read-heavy workloads under the lock-contention threshold.

## Migration sequence

1. **Stand up Postgres + TimescaleDB** — Docker is fine for dev/staging.
   For production, use a managed service (Timescale Cloud, RDS with
   TimescaleDB extension, or self-hosted PG with the extension).

   Quick-start (Docker, local):
   ```bash
   docker run -d --name marketlens-tsdb \
     -e POSTGRES_PASSWORD=changeme \
     -p 5432:5432 \
     -v marketlens_pgdata:/var/lib/postgresql/data \
     timescale/timescaledb:latest-pg16

   psql postgresql://postgres:changeme@localhost:5432/postgres \
     -c "CREATE DATABASE marketlens;"
   ```

2. **Update `.env`** — point `DATABASE_URL` at the new database:
   ```
   DATABASE_URL=postgresql+psycopg2://postgres:changeme@localhost:5432/marketlens
   ```
   (Don't restart the live backend yet.)

3. **Create base tables in Postgres** — runs SQLAlchemy's
   `Base.metadata.create_all()` once against the new URL:
   ```bash
   cd backend
   python -c "from app.database import Base, engine; Base.metadata.create_all(engine)"
   ```

4. **Copy data from SQLite → Postgres**:
   ```bash
   python migrations/002_migrate_from_sqlite.py \
     --sqlite=marketlens.db \
     --postgres="$DATABASE_URL"
   ```
   The script is idempotent — re-running just re-attempts any rows that
   failed.

5. **Apply TimescaleDB hypertable conversion**:
   ```bash
   psql "$DATABASE_URL" -f migrations/001_timescaledb_setup.sql
   ```
   This converts `ohlcv_bars` into a hypertable, enables compression on
   chunks >30d old, sets the 5-year retention policy, and creates the
   `ohlcv_daily_summary` continuous aggregate.

6. **Restart the backend** — it picks up the new `DATABASE_URL` from
   `.env` and starts using Postgres immediately.

7. **Verify**:
   ```bash
   # Smoke-test the backend
   curl http://localhost:8000/api/health?detailed=true

   # Verify hypertable
   psql "$DATABASE_URL" -c "
     SELECT hypertable_name, num_chunks, compression_enabled
     FROM timescaledb_information.hypertables;
   "
   ```

## Rollback

If something goes wrong: just point `DATABASE_URL` back at SQLite
(`sqlite:///./marketlens.db`) and restart. The original SQLite file is
untouched by the migration script.

## What changes after migration

- All read/write paths continue working — SQLAlchemy abstracts the
  dialect difference.
- `ohlcv_bars` date-range queries become ~100× faster on large datasets.
- Disk usage drops ~10× for compressed chunks (older than 30 days).
- You can safely run multiple uvicorn workers in production.
- The `auth_service` login rate limiter automatically swaps to Redis if
  you also set `REDIS_URL`.

## Future migrations

Add new SQL/python scripts here as `003_*.sql`, `004_*.py` etc. We
deliberately don't use Alembic — the migration count is low enough that
plain scripts are easier to reason about than autogenerated migration
chains.
